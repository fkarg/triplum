# Stages: checkpointed, content-addressed processing steps and replicated experiments

Snapshot 2026-09-17. Status: **contract, agreed with the owner in conversation; the review record
below is filled at the design gate.** Makes design D6a true and amends it; adds the replicate
rule to D8; leaves D5 as it is. The requirements R6 to R13 of
[`2026-09-17-caching-and-monitoring.md`](2026-09-17-caching-and-monitoring.md) are satisfied
through this contract. Work and commit on local main.

## Why

D6a promises that every expensive stage is content-addressed on its inputs and config, persists
its output and is skipped on rerun. The caching audit found this is not true end to end: two
stages recompute on every run, a stage output has no home except the single-slot store, the
code identity is a hash of whole module files per pipeline, and nothing a rerun can resume from
is written before a stage runs.

The owner's direction, in their words: processing steps have a before and after checkpoint,
record their config and input dependencies, cache their results, and fetch rather than
recompute, because every step is cheaper to fetch than to compute. Document text to chunks is
one such step and later steps build on cached results. Experiments must be able to rerun the
whole pipeline several times, fully deterministic, with automatic per-step variance analysis:
which steps add variance, which reduce it. By default an experiment is one run, all cached; the
replicates are cached too and the first is the default one. And, decisive for the identity:
this is a library whose users override parts of it, so the identity of a step must be a
fingerprint of the data and a fingerprint of the code that will actually execute, not a static
version string that nobody bumps when a helper three calls down is replaced.

Prior art checked (2026-09-17, sourced research in the conversation record): Hamilton, Dagster,
Prefect, DVC, Metaflow, Kedro, Luigi, Bazel, Nix, joblib, HF datasets, redun, checkpointer,
pytest-testmon, ccache, ninja, Sacred, MLflow, W&B, Hydra. Two facts shaped the contract. No
framework caches a stream as a stream; Prefect consumes generators to a list and Hamilton forces
recompute on generator nodes. And no Python tool combines runtime-discovered callee sets with
normalised per-function hashes: testmon has the trace half, checkpointer the normalised-hash and
captured-globals half, both scope third-party code by distribution version. The soundness of
recorded dependency sets is the argument build systems use for discovered inputs (ccache's
manifests, ninja's depfiles, Bazel's `.d` pruning, the verifying traces of Mokhov et al.).

## Terms

- **Stage**: a plain function that computes one processing step, wrapped so it has an identity
  and a checkpoint. D5 holds: a pipeline is a plain function calling stages.
- **Artifact**: the persisted output of a stage, addressed by the stage's identity.
- **Invocation**: one call of a stage inside a run; its row in the run store is the checkpoint,
  written before the function runs and completed after.
- **Experiment**: a configuration, a root seed and a replicate count. Replicate 0 is the run.
- **Data fingerprint**: what the stage is asked to do. **Code fingerprint**: what code did it.

## Contract

### Identity

A stage's identity is two fingerprints on two independent axes, and an artifact is addressed
by the pair. A change on the data axis (a new source revision, a different config, another
replicate's seed) is a new address whose lookup reuses the code manifests already recorded for
the stage. A change on the code axis (an edited function, an overridden helper) reruns exactly
the stages whose manifests contain it, against fetched inputs, and nothing upstream. Neither
axis ever forces a recompute on the other.

The **data fingerprint** comes in two forms. The **structural key** is
`content_key("stage", [name, inputs, config])`; the **execution key** adds the derived seed
when the stage is seeded (below). Both are known before the stage runs. The execution key
addresses the artifact; the structural key is stable across replicates and is what the
variance report joins on. `name` is the stage's module and qualified name. `inputs` are the
identities of the arguments, in signature order:

| argument | identity |
|---|---|
| a `Dataset` or `IterableDataset` | its `fingerprint()` |
| an artifact (an `Artifact`, a live or published stream, a frame or record list a stage of this run produced or fetched) | its data key, and nothing else |
| a store | its identity: corpus and graph identities from its meta table (R14) |
| a pydantic model or frozen dataclass | its canonical dump |
| an adapter (LLM, embedder, reranker, extractor) | its spec's hash |
| `str`, `int`, `float`, `bool`, `None`, tuples of these | the value |
| anything else | `TypeError` at call time, never a random key |

Every argument that is not plain data or an artifact also contributes the qualified name of
its type. This closes the one hole in discovered dependencies: a dispatch target that did not
exist when the manifest was recorded. A user who passes a subclass of `SqliteStore` changes
the data fingerprint and the stage runs and records a new manifest. An artifact is identified
by its data key alone, never by its type or its code, so a live stream and its replay from the
cache key a downstream stage the same, and a downstream key exists before an upstream stream
has been exhausted (a live stream has no code fingerprint until then). A `Viewer` is its
principals and permission revision; its as-of instants default to now and stay outside
identity, as on the run record, until the temporal fixtures make them explicit.

**The code axis is validated, not addressed.** An artifact directory is `<key>/<code>/` and
the row is keyed by both, but a downstream key never contains an upstream code. At lookup, a
candidate at the key is fetched when its own manifest validates, it is complete on disk, and
every artifact it was built from (the `invocation_inputs` edges, followed transitively) is
valid by the same test. A code edit upstream therefore invalidates downstream through the
lineage, and nothing upstream of the edit recomputes.

`config` is the stage's own configuration, a pydantic model. A stage is **seeded** when it takes
a `seed` parameter or when any of its arguments is a seed-sensitive adapter; the wrapper decides
this from the signature and the arguments, so a stage cannot call a seed-sensitive adapter and
still be fetched across replicates. A stage seeded through an adapter reads its derived seed
with `stage_seed()` (0 outside a run), so that a stage whose adapters are all seed-insensitive
is fetched across replicates rather than rerun for a seed it would not use.

The **code fingerprint** is the hash of a **manifest**: the set of first-party functions the
stage executed, each with a normalised source hash, plus the version of every third-party
distribution whose code ran, plus the fixed non-Python inputs. It is discovered by execution and
is therefore known only after the stage has run once. That is not a limitation: a stage that has
never run has nothing to fetch.

- **Discovery.** `sys.monitoring` with a `PY_START` callback records every code object entered
  and disables itself for that code object, so the cost after the first entry is nil (measured
  on the BM25 stage: no difference inside timer noise; on a 300k-call recursion: 1.01×). The
  tracer is enabled once per process because toggling costs hundreds of milliseconds; a stage
  restarts events on entry and records until its work is done. For a value-returning stage that
  is the return; for a streamed stage the wrapper owns the iterator and records during every
  pull until exhaustion or close, because the generator body runs then, not at the call.
  Monitoring is per interpreter, so code entered on any thread while a stage is active is
  attributed to it; that is a superset, which invalidates more, never less. Stages are
  synchronous; a coroutine is not a stage. Subprocesses and native code are not traced (below).
  A stage called from inside a stage contributes its manifest to both.
- **First-party** is decided by file path: a code object whose file is not under the
  interpreter's `purelib`, `platlib` or standard library paths is first-party. This treats
  editable installs and a user's own modules as source, which is what distribution metadata
  gets wrong. Third-party code is recorded as `(distribution, version)` for the distribution
  that owns the module, with the version taken whole.
- **Granularity** is the outermost function or method: a nested function, lambda or generator
  expression is recorded under the function that contains it and hashed as part of it.
- **Normalised hash.** The function's source through `inspect.getsource`, parsed, docstrings
  removed from every function, class and module body, hashed as `ast.dump` without positions.
  Comments, whitespace and docstrings do not change it; a signature, decorator, default or body
  change does. A code object without retrievable source (a REPL without `linecache`) is hashed
  from its bytecode and constants and recorded as such.
- **Module constants.** For every recorded function, each global name it loads that resolves to
  plain data (the table above, plus `dict` and `list` of plain data) enters the manifest by
  canonical value. The reader's prompt is a module constant and is covered this way, which is
  the rapid-experimentation case: edit the prompt, rerun, and the read stage recomputes while
  retrieval is fetched. Nothing else referenced through a global is captured.

**Rules for stage authors**, stated once and enforced by nothing but the consequence: a stage
reads everything that shapes its output from its arguments, its config, its own body and the
functions it calls. Dispatch through a mutable module-level registry, a closure over mutable
state, a module-level adapter or store instance, an environment variable, or a global that is
mutated at run time is invisible to the fingerprint and yields stale artifacts. Do not do it;
pass the collaborator as an argument, where the identity table applies. The one registry in
the codebase, the pipelines table, is consulted by the runner before any stage runs and names
the stage functions themselves, so it is outside every manifest by construction.
- **Fixed inputs.** The Rust extension's build identity and the SQL migrations file are in every
  manifest. A stage whose adapter runs a subprocess relies on that adapter's spec (the CLI
  adapter's argv and model) for identity, as today.

**Lookup.** Given a stage call, compute the execution key, select the artifacts at that key,
and for each candidate re-hash its manifest against the current process: resolve each entry's module and qualified name (unwrapping decorators, taking a
property's getter, a static or class method's function), hash the current source, compare, and
compare distribution versions and referenced state. The first candidate whose manifest matches
and whose artifact is present and complete is fetched. A monkeypatched function resolves to the
replacement and mismatches. An entry that cannot be resolved is a mismatch: a needless miss is
safe, a stale hit is not. No match: run, record.

Soundness, and its limits, stated: under the author rules, a rerun that would execute
different code gets there through a changed function body, a changed plain-data constant, or a
changed argument type, and each is in the recorded set or the data fingerprint; branches taken
on data are covered by the data fingerprint. Outside the rules the fingerprint is silent, and
the rules say so. Also not covered: native code and subprocesses (identity comes from their
spec), `Settings` (never part of an identity, as before), and nondeterminism, which the seed
rule makes explicit rather than hidden.

### The stage interface

```python
@stage
def chunk(docs: Source[Document], cfg: ChunkConfig) -> IterableDataset[Chunk]: ...


@stage
def retrieve(
    qa: Source[Question], store: Store, cfg: RetrieveConfig, seed: int
) -> pl.DataFrame: ...
```

`stage` wraps a plain function. Calling the wrapper runs the lookup above, then either fetches
the artifact or runs the function under discovery, persists the result, and writes the
checkpoint. The wrapped function is reachable as `chunk.fn` for tests that want the computation
without the cache. The wrapper takes a `Run` context (run store, artifact root, seed derivation)
from a context variable set by the runner, so stages compose without threading a handle through
every call; calling a stage with no context runs the function directly, uncached, which is what
a notebook cell exploring a step wants.

Outputs, by return type:

- A polars frame or a list of pydantic records: persisted whole under the artifact key. The
  run remembers the object it returned (computed or fetched) so a later stage that takes it
  records the artifact edge; a stage that wants one record returns a list of one.
- An `IterableDataset` of records or an iterable of frames: **teed** to parquet batches as it
  yields, so the consumer streams and the artifact fills up behind it. The checkpoint is
  completed on exhaustion. A partial artifact is never read; an interrupted stream restarts.
  Replaying a fetched stream artifact yields the records batch by batch, so a downstream stage
  streams from the cache too. The artifact reports the content hash and the record count on
  completion. A downstream stage that consumed only part of a live stream (a `Take`) has an
  input with no completed artifact; its invocation is recorded and its output is returned but
  not published, and the producer's invocation is marked `partial`.
- `None`, for a stage whose effect is in the store (ingestion, embeddings, the graph). The
  store owns the record of that effect in its own tables: the ingestion log (corpus identity,
  started, completed, per-batch progress), the embedding specs present, the graph identity. A
  store-effect stage's lookup asks the store, not the run store, whether the effect with this
  execution key is complete, so a recreated or partially written store file is never mistaken
  for a finished one. The run store's checkpoint records the invocation and whether it fetched
  or executed.

### Provenance: artifacts, invocations, manifests

Four tables in the run store, in the entity, activity and used shape of provenance records, so
lineage and bookkeeping are queries rather than conventions:

`artifacts`, one row per completed output, immutable:

| column | content |
|---|---|
| `key`, `code` | execution key and code fingerprint; together the primary key and the path |
| `stage` | module and qualified name |
| `kind` | `frame`, `records`, `stream`, `store` |
| `content_hash`, `rows`, `bytes` | of the published artifact |
| `created_by` | the invocation that produced it |
| `created_us` | instant |

`invocations`, one row per stage call inside a run, written with `running` before the function
runs and completed after; this is the checkpoint:

| column | content |
|---|---|
| `id`, `run_id` | the invocation and its run |
| `stage`, `structural_key`, `key`, `code` | what was asked, with and without the seed, and what code answered |
| `config_json` | the config dump, for `inspect` and `diff` |
| `seed`, `replicate` | the derived seed and the replicate index |
| `fetched` | whether the artifact was fetched or produced |
| `status`, `error` | `running`, `ok`, `failed`; the exception text |
| `started_us`, `finished_us`, `wall_s` | instants and duration |
| `host` | bookkeeping only |

`invocation_inputs`, the edges: `invocation_id`, `position`, `kind` (`artifact`, `source`,
`store`, `config`, `adapter`, `value`), `identity` (the artifact key and code, the source
fingerprint, the store identity, the config or spec hash, the value). Lineage of an artifact is
the recursive walk from its `created_by` invocation over these edges; "which runs used this
artifact" and "what did this code change orphan" are the same table read the other way.

`manifests`: `code` to `manifest_json`, one row per distinct manifest. Manifests repeat across
every invocation of a stage until its code changes, so they are stored once and referenced.

`runs` gains `experiment_id` and `replicate`. The existing `events` table keeps timing and
usage per stage and per question, linked to invocations by id. A failed invocation removes its
temporary directory; a published artifact is never removed except by `cache prune`. Progress
rows (D-c) are updated by the stage wrapper for streamed outputs, one row per running
invocation with done and total where total is known.

Artifacts live under `artifacts/<stage>/<key>-<code>/` in the cache root, per D-b; frames as
one parquet file, records as parquet through the collator's schema, streams as numbered parquet
batches. Every kind is written to a temporary directory and published by one atomic rename,
and every kind carries a `complete` record written last with the content hash, the record count
and the file sizes; a lookup requires the row, the record and matching sizes before it fetches.
Two processes producing the same key both compute; the second rename finds the directory present
and discards its own, so a published artifact is never replaced. `triplum cache status` sizes
them by stage.

### Seeds and replicates

An experiment has a root seed and `replicates`, default 1. Replicate `r` has the seed
`derive(root, r)`; a stage with a `seed` parameter receives `derive(replicate_seed, stage name)`,
so stages draw independently and one stage's consumption never shifts another's, as Sacred does.
`derive` is a content key truncated to 64 bits.

An adapter declares `seed_sensitive`. When true, the derived seed is part of its call cache key
and, where the provider accepts one, is sent with the request; when false the seed is ignored
and every replicate is served from the same cache entry. Defaults: LLM adapters true, embedders
and rerankers false, the fake adapters false. This is a choice: GPU float noise in embeddings is
real but is not what the owner wants to measure; a rerun mode that varies embedders is a later
option. Whether a provider honours the seed is recorded on the run (R4).

The execution key includes the derived seed only for seeded stages. A stage downstream of a
seeded stage reruns per replicate through its input identity; a stage upstream is fetched. Two
replicates colliding on a 64-bit derived seed is a negligible probability and is not handled. Nothing else is needed for "the ten runs are cached": each replicate is a
run in the run store with its own checkpoints, and replicate 0 is what `bench` reports when no
replicate is named.

### Experiments and the variance report

`run_experiment(cfg, replicates=n)` runs the pipeline `n` times under seeds derived as above and
returns the run ids, first the default. The run store groups them by an experiment id, the
content key of the configuration and the root seed. The report joins the invocations of the
replicates by structural key, which names one logical invocation (the same stage called per
question joins per question) and is equal across replicates by construction:

- **inputs agree**: the content hashes of the invocation's input artifacts are equal across
  replicates (for sources and configs, always);
- **outputs agree**: its content hashes are equal across replicates;
- a stage with inputs agreeing and outputs differing **adds variance**; one with inputs
  differing and outputs agreeing **absorbs** it; both agreeing is deterministic; both differing
  passes variance through. The report marks which invocations were fetched rather than
  executed: a fetched stage was not observed to be deterministic, it was not run.

The report measures variance under the chosen seed policy, not all execution variance. A
seed-insensitive adapter recomputed after eviction may produce different bytes under the same
address; the downstream key is input-addressed, so that difference is invisible by design and
is stated here rather than chased.

### What changes in the existing code

- `bench/fingerprint.py` and the per-pipeline module lists go. A run's code identity is the set
  of code fingerprints of its stages, recorded per invocation; `code_hash` on the run becomes
  the hash of that set. `inspect` and `diff` show which stage's code changed between two runs,
  which the module-list hash could not.
- `ensure_documents`, `ensure_embeddings`, `ensure_graph`, `_retrieve`, the read loop, the judge
  and the scorer become stages. `CachedExtractor` keeps its per-chunk call cache; the extract
  stage's artifact is the spans and claims for the whole corpus, so grounding and resolution
  (two further stages) run once per identity (R7, R9, R10).
- `RunConfig`, `ExtractConfig` and the adapter configs become pydantic models; `to_json` and
  `from_json` are `model_dump_json` and `model_validate_json`. `seed` stays on `RunConfig` as
  the root seed; `replicates` joins it.
- `materialize` stops being called for an identity lookup: a run's identity is computed from
  source fingerprints and config before any read (R6, gap 8). Materialisation, where an
  algorithm still needs it, is a stage with a `records` artifact (R7).
- The run identity fields are one list, shared by the run store, `benchmarking.md` and `diff`
  (R15). `store` artifacts are recorded by identity, not file hash (R14).
- Layer 1 of the stack walk, the ingestion boundary, is built as stages: the store owns its
  ingestion log and the ingest stage is a store-effect stage over it; the chunking stage
  `[Document] -> [str] -> [str]` is the first streamed stage.

## Consequences for callers

- A notebook calls `chunk(docs, cfg)` and gets a stream, uncached; the same call inside a run
  is fetched the second time. Nothing about the function changes between the two.
- A user who overrides a library helper, monkeypatches a stage or passes their own store
  subclass gets a recompute, not a stale artifact, without declaring anything.
- Cosmetic edits, docstrings and comments never invalidate a checkpoint. A change to a constant
  a stage reads does.
- Every replicate of an experiment is a run; the report is the only new surface.

## Non-goals

- A DAG framework, a scheduler, or a registry of stages (D5). The wrapper adds identity and a
  checkpoint to a function and nothing else.
- Resuming an interrupted stream artifact mid-way. It restarts.
- Cross-machine artifact sharing (D9: the cache is per machine).
- Per-stage numeric variance distances; a rerun mode that varies embedders; thread-local
  tracing (monitoring is per interpreter).
- Fingerprinting code executed in subprocesses or native extensions beyond their spec.

## Acceptance

- A second identical run fetches every stage: zero function executions, checkpoints `ok`, run
  served from the run store without reading a dataset.
- Editing a comment or docstring anywhere in the executed code changes no code fingerprint;
  editing the body of a helper called only through dynamic dispatch, or monkeypatching a stage,
  changes exactly the fingerprints of the stages that executed it.
- Passing a subclass of the store with one overridden method reruns the stages that took the
  store and fetches the rest.
- A streamed stage consumed by a downstream stage never materialises the stream in memory; the
  artifact completes on exhaustion and a rerun streams from it batch by batch; an interrupted
  stream leaves no readable artifact.
- An experiment with three replicates on the fixture with a fake reader reports every stage
  deterministic; with a seed-sensitive fake reader that perturbs on seed, the read stage adds
  variance, retrieval is fetched, and the metric table shows a non-zero standard deviation.
- Discovery overhead on the BM25 stage over the fixture stays within timer noise.

## Review record

- 2026-09-17, `peer-review --mode design`, peer: Codex (GPT family), verdict "challenges", seven
  falsification attempts of which two were local probes on the project's Python 3.13.
  **Changed the decision** on five findings, all folded into the contract above: discovery for a
  streamed stage covers every pull until exhaustion, not the call (probe: tracing until return
  saw only the outer function); the report joins on a seed-free structural key and the cache on
  an execution key with the seed (substituting the seed rule into the classifier showed a
  seeded stage could never be classified as adding variance); the store owns the record of a
  store effect and a store-effect stage's lookup asks the store (an `ok` checkpoint proves a
  process once finished, not that the store file still holds the effect); a stage is seeded
  when any argument is a seed-sensitive adapter, not only when it takes a seed; every artifact
  kind publishes atomically with a completion record and sizes, unresolvable manifest entries
  are a miss. **Added verification**: the resolver at lookup is tested against decorated
  methods, closures, properties, static and class methods, local functions, `exec` and reloads;
  the report states it measures variance under the seed policy and marks fetched invocations.
  **Refuted the soundness argument as first written** (probe: a stage dispatching through a
  mutable module-level registry, registry edited, manifest still matched): the contract now
  captures referenced globals, closure cells, containers and singledispatch registries by
  structure, and forbids module-level mutable object state for cacheable stages; the residual
  hole is stated. The peer's counterproposal, one conservative pre-execution hash over all
  loaded first-party source applied to every stage, is the alternative if the owner judges the
  residual too large; it is sound against the same list except runtime mutation, needs no
  tracer, and recomputes everything on any edit anywhere, which forfeits per-stage fetch and
  per-stage code attribution. **Rejected as not meeting the requirement**: spooling a stream to
  parquet before exposing it downstream, which gives up producer-consumer pipelining; the
  lifetime fix addresses the concern it was raised for. **Owner's decision (2026-09-17)**: the counterproposal recomputes too often for a library meant
  for reformulating one stage and rerunning just that part; the trace manifest stays, with the
  capture cut to plain-data module constants and the rest made an author rule. The checkpoint
  table was reconsidered for traceability and became the provenance tables above.
- 2026-09-18, `peer-review --mode diff-review` over the four commits, peer: Codex (GPT
  family), verdict "challenges", five falsification probes run in isolated temporary runs.
  **Found unique defects, all fixed with regression tests**: a store-effect stage was fetched on
  the store's word alone, so an edited `ingest` left the old effect in place (now the recorded
  manifest must validate too, else the idempotent effect runs again); an exhausted empty stream
  crashed at publication and left its invocation `running` (now publishes an empty artifact,
  and a stream artifact records whether it holds records or frames); the judge's endpoint,
  argv and generation parameters were outside the run identity (`judge_hash` added to the
  identity fields); a bare dict of frames carried no type. **Rejected as a false positive**:
  "a stored run is returned after its artifact directory or store file disappeared". A run is a
  recorded result, not a cache entry; its validity is whether the same code would produce it,
  which the manifests of every stage it ran decide, and those cover the lineage because each
  stage is an invocation of the run. **No decision impact**: three dead-code nits, removed.
- 2026-09-18, commit 3: the `answer` stage's artifact holds content columns only; latency, cost
  and cache state go to the run's question rows, so two executions with equal answers hash
  equal and the variance report is not fooled by timing.
- 2026-09-18, implementation of commit 1 changed three points of the approved text, recorded
  in place above: a downstream key contains upstream data keys only and the code axis is
  validated along the lineage (a live stream has no code fingerprint until exhausted, so the
  approved input-addressing by key and code could not give a downstream key before the stream
  ran); artifacts are identified by key alone, never by type; a stage returns a frame, a list
  of records, a stream or nothing, the single-model return was dropped.
