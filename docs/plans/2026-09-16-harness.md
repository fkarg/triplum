Snapshot 2026-09-16, squashed on 2026-09-17. The two original plans were near-complete source
listings (4,700 lines) that drifted from the code by construction; this page keeps what a
development record needs, and git history (`git show 13a6fa3^:docs/plans/`) keeps the rest.
Spec: [`../specs/2026-09-16-harness-and-baselines.md`](../specs/2026-09-16-harness-and-baselines.md).
Design: D2, D4, D5, D6, D6a, D7, D8 in `docs/research/design.md`.

## Part 1: scaffold, data layer, SQLite store, model protocols

Goal: a buildable package (Python over a small Rust core) with the canonical Arrow schemas, a
SQLite store that filters BM25 and vector search by viewer inside the index, and cached,
swappable LLM, embedder and reranker protocols with fakes for tests. Stack: uv, maturin (mixed
layout), PyO3 with pyo3-arrow, polars, pyarrow, numpy, sqlite-vec, the openai SDK, pytest.

1. Scaffold that builds: workspace, `triplum-core` schemas, `triplum-py` bindings, `_core.pyi`.
2. `Viewer` (principals, as-of valid and recorded instants).
3. Content-addressed disk cache.
4. `LLM` protocol, fake, cached wrapper keyed on the full effective request.
5. OpenAI-compatible and CLI-subprocess LLM adapters.
6. `Embedder` protocol with `EmbeddingSpec`, fake, cached wrapper, OpenAI-compatible adapter.
7. Local embedders: sentence-transformers and fastembed (the `local` extra).
8. `Reranker` protocol, fake, cross-encoder adapter.
9. SQLite store: migrations, documents, grants, chunks with viewer filtering.
10. BM25 through FTS5 with the ACL token column inside the match.
11. Vector search through sqlite-vec, partitioned by principal-set hash.

Self-review at the time: spec items 1 to 6 covered; `Capabilities` defined and only reported;
datasets, pipelines, metrics, run store, CLI and notebook deferred to part 2.

## Part 2: datasets, baselines, metrics, run store, CLI

Goal: `triplum bench run --pipeline dense --dataset musique --n 20` produces a run with EM, F1,
Contain-Acc, Judge-Acc, R@2, R@5, tokens, cost and latency for the non-graph baselines on the
HippoRAG 1000-question protocol data, with the embedder as a swappable spec.

1. Dataset loader for the HippoRAG protocol files, pinned hashes, 20-question fixtures.
2. Metrics as pure functions.
3. Retrieval stages returning a `(question_id, chunk_id, rank, score)` frame; one reader prompt.
4. Frozen configs and factories.
5. Run store with events and prices.
6. Indexing, runner, report; run lookup by identity.
7. CLI, marimo notebook, embedding sweep.

Deviations recorded then: the corpora come from the HippoRAG release files (MIT repo, content
under the upstream licences) with pinned hashes rather than a rebuild from upstream; hierarchical
chunking moved to the 2a plan; no `--cache-only` flag (a fully cached run shows zero misses,
which is the same evidence).

## What changed after

Everything in this plan is implemented; the current state is `docs/flow.md`. Since then: the
dataset registry grew to 37 sets with per-source parsers and a local-files loader; retrieval
pipelines became named functions in `retrieve/pipelines.py` with an `rrf` baseline; the run
store owns its connection and gained resume and migrations; `n_passages` became `n_chunks`.
