# Local run logs, cache, and inspection: AOM lessons for triplum

Scope and evidence: this is a source-reading comparison as of 2026-09-16.  “AOM” below is `/Users/felix/Coding/ansible-aom`; file references are absolute repository-relative paths with source line numbers. Recommendations are explicitly marked as recommendations rather than claims about current behaviour.

## 1. AOM event log: implementation, recovery, replay, and lifecycle

### Layout, record shape, and versions

A live AOM session is a UUIDv7-named directory under the session state directory. Its working layout is `events.jsonl` plus `meta.json`; completion also creates a derived `index.db` and may create `diagnostics.json`. Completed sessions can be exported into a single `.aom` JSONL artifact whose first record is metadata, intervening records are events wrapped with `type: "event"`, and final record is a stats summary. [`src/ansible_aom/session/store.py:244-258`](../../../../ansible-aom/src/ansible_aom/session/store.py#L244-L258), [`src/ansible_aom/session/store.py:585-660`](../../../../ansible-aom/src/ansible_aom/session/store.py#L585-L660)

`meta.json` initially records the playbook, argv, UTC start time, package `version`, session ID, and `_schema_version: 2`; readers treat missing `_schema_version` as legacy schema 1. [`src/ansible_aom/session/store.py:314-374`](../../../../ansible-aom/src/ansible_aom/session/store.py#L314-L374), [`src/ansible_aom/session/store.py:783-819`](../../../../ansible-aom/src/ansible_aom/session/store.py#L783-L819) Event records are full original event dictionaries, not a lean projection, because inspect later seeks their payloads by byte span; stderr is represented as a synthetic `aom_stderr_line` event in that same log. [`src/ansible_aom/session/store.py:54-61`](../../../../ansible-aom/src/ansible_aom/session/store.py#L54-L61), [`src/ansible_aom/session/store.py:395-430`](../../../../ansible-aom/src/ansible_aom/session/store.py#L395-L430)

The event envelope is therefore versioned only indirectly through its producer/event type rather than through a per-line schema marker. The derived index has an explicit `INDEX_SCHEMA_VERSION = 1`, stored with the event file size and nanosecond mtime; its schema includes aggregate host/play/task/task-host tables, stderr rows, connections, and byte offsets/lengths for payload rehydration. [`src/ansible_aom/session/index.py:47-74`](../../../../ansible-aom/src/ansible_aom/session/index.py#L47-L74), [`src/ansible_aom/session/index.py:112-128`](../../../../ansible-aom/src/ansible_aom/session/index.py#L112-L128)

### Append, durability, and failure handling

The hot path serializes an event to UTF-8 JSON plus newline and performs a non-blocking enqueue into a bounded queue of 1,000 entries. A daemon writer opens `events.jsonl` once with unbuffered append mode (`"ab", buffering=0`) and calls `write()` per queued line; it does not call `fsync`. Queue overflow increments a dropped-event counter rather than slowing the renderer, and disk errors are retained as an asynchronous reason while the writer drains queued items as no-ops. [`src/ansible_aom/session/store.py:47-61`](../../../../ansible-aom/src/ansible_aom/session/store.py#L47-L61), [`src/ansible_aom/session/store.py:107-241`](../../../../ansible-aom/src/ansible_aom/session/store.py#L107-L241), [`src/ansible_aom/session/store.py:376-393`](../../../../ansible-aom/src/ansible_aom/session/store.py#L376-L393)

This is deliberately a responsiveness-over-completeness choice, not a durable append protocol: AOM’s own comments say a crash can lose the last unflushed write, and its concurrent-read test describes no-fsync operation as intentional. [`src/ansible_aom/session/store.py:217-221`](../../../../ansible-aom/src/ansible_aom/session/store.py#L217-L221), [`tests/integration/test_concurrent_inspect.py:80-83`](../../../../ansible-aom/tests/integration/test_concurrent_inspect.py#L80-L83) On normal completion it drains and joins the writer before reading the log for index construction, then updates `meta.json` with status, end time, duration, and preflight counts. [`src/ansible_aom/session/store.py:442-514`](../../../../ansible-aom/src/ansible_aom/session/store.py#L442-L514)

Recovery is reader-side degradation. `load_session()` parses each nonempty binary line independently; malformed JSON or invalid UTF-8 increments `malformed_lines` and is skipped. Missing `meta.json` logs a warning but returns parsed events, while replay defaults the absent status to `completed`. [`src/ansible_aom/session/store.py:822-894`](../../../../ansible-aom/src/ansible_aom/session/store.py#L822-L894), [`src/ansible_aom/drivers/replay.py:91-131`](../../../../ansible-aom/src/ansible_aom/drivers/replay.py#L91-L131) The derived-index builder follows the same malformed-line skip policy, and protects publication with a pre/post `(size, mtime_ns)` comparison plus atomic `os.replace()` from a PID/TID-unique temporary database. [`src/ansible_aom/session/index.py:134-219`](../../../../ansible-aom/src/ansible_aom/session/index.py#L134-L219)

The tests substantiate that recovery contract: their stated expected failure shape is events present with missing or truncated meta, their loader tests require events and warning to survive missing metadata, and their subprocess scenario SIGKILLs a real writer and expects a fresh replay process to exit successfully with surviving events. [`tests/unit/test_event_store_crash_recovery.py:1-61`](../../../../ansible-aom/tests/unit/test_event_store_crash_recovery.py#L1-L61), [`tests/unit/test_event_store_crash_recovery.py:241-301`](../../../../ansible-aom/tests/unit/test_event_store_crash_recovery.py#L241-L301), [`tests/unit/test_event_store_crash_recovery.py:386-414`](../../../../ansible-aom/tests/unit/test_event_store_crash_recovery.py#L386-L414)

### Replay, collectors, redaction, retention

Replay loads the recorded session, omits synthetic stderr events because they were not delivered to the original renderer, retains file order, and sleeps on non-negative timestamp deltas scaled by `--speed`. It always closes the renderer and maps Ctrl-C to completion `(130, "crashed")`; the unit tests pin order, speed scaling, negative-delta clamping, completion status, and interruption behaviour. [`src/ansible_aom/drivers/replay.py:65-164`](../../../../ansible-aom/src/ansible_aom/drivers/replay.py#L65-L164), [`tests/unit/test_replay.py:40-193`](../../../../ansible-aom/tests/unit/test_replay.py#L40-L193), [`tests/unit/test_replay.py:196-320`](../../../../ansible-aom/tests/unit/test_replay.py#L196-L320)

The useful reusable abstraction is not JSONL itself: storage is isolated in `session/store.py`, while pure session projections consume a loaded event dict. `collect_failed_hosts`, `collect_unreachable_hosts`, and `collect_changed_hosts` return deduplicated host sets by scanning the relevant event/result shapes; their unit tests cover empty sessions, multi-host records, repetition, and irrelevant event types. [`ARCHITECTURE.md:311-313`](../../../../ansible-aom/ARCHITECTURE.md#L311-L313), [`src/ansible_aom/session/summary.py:1-12`](../../../../ansible-aom/src/ansible_aom/session/summary.py#L1-L12), [`src/ansible_aom/session/summary.py:45-124`](../../../../ansible-aom/src/ansible_aom/session/summary.py#L45-L124), [`tests/unit/test_session_collectors.py:15-192`](../../../../ansible-aom/tests/unit/test_session_collectors.py#L15-L192)

Before rendering or recording, AOM’s redactor copies the event, honors `_ansible_no_log`, recursively redacts exact and configured key matches, sanitizes credential-looking values in selected string fields, and also redacts verbose `invocation.module_args`. The key-matching rewrite avoids an earlier false-positive/bypass class caused by an old broad password regex; this is a genuine recorded pain point, though it concerns Ansible payloads rather than triplum’s current call cache. [`src/ansible_aom/core/redaction.py:1-27`](../../../../ansible-aom/src/ansible_aom/core/redaction.py#L1-L27), [`src/ansible_aom/core/redaction.py:124-199`](../../../../ansible-aom/src/ansible_aom/core/redaction.py#L124-L199), [`src/ansible_aom/core/redaction.py:255-310`](../../../../ansible-aom/src/ansible_aom/core/redaction.py#L255-L310)

Retention is simple destructive cleanup: sessions are sorted by metadata start time (directory mtime fallback) and deleted when beyond `keep_count` (default 100) or older than `keep_days` (default 30); `aom inspect prune --days` exposes the age portion. The architecture estimates that verbose 200-host sessions can be ~50 MB and 100 such sessions ~5 GB. [`src/ansible_aom/session/store.py:665-728`](../../../../ansible-aom/src/ansible_aom/session/store.py#L665-L728), [`src/ansible_aom/inspect/cli.py:184-188`](../../../../ansible-aom/src/ansible_aom/inspect/cli.py#L184-L188), [`ARCHITECTURE.md:155-161`](../../../../ansible-aom/ARCHITECTURE.md#L155-L161)

## 2. AOM cached reading and `inspect`

AOM keeps JSONL authoritative and uses `index.db` solely as a disposable acceleration layer. Building it streams the log once, records task/host aggregates and event spans, batches stderr inserts at 10,000 rows, and disables SQLite journalling/synchronous durability because the temporary database is safe to lose before atomic rename. Freshness is size plus mtime, and a session still growing or changing during build is left without a published index. [`src/ansible_aom/session/index.py:1-15`](../../../../ansible-aom/src/ansible_aom/session/index.py#L1-L15), [`src/ansible_aom/session/index.py:131-219`](../../../../ansible-aom/src/ansible_aom/session/index.py#L131-L219)

The inspect text fast path reads only metadata and the index, asking for host rows only for failures (and an explicitly requested task); it lazily seeks just the failed event lines for detail. Its own code describes the resulting warm-open complexity as O(failures), even for hundreds of thousands of task-host pairs; verbose stderr is queried with SQL filtering instead of materialized wholesale. [`src/ansible_aom/inspect/cli.py:129-165`](../../../../ansible-aom/src/ansible_aom/inspect/cli.py#L129-L165), [`src/ansible_aom/inspect/text.py:287-359`](../../../../ansible-aom/src/ansible_aom/inspect/text.py#L287-L359), [`src/ansible_aom/session/index.py:424-441`](../../../../ansible-aom/src/ansible_aom/session/index.py#L424-L441), [`src/ansible_aom/session/index.py:586-650`](../../../../ansible-aom/src/ansible_aom/session/index.py#L586-L650) There is no benchmark establishing an “instant” latency, so no numeric latency claim is justified.

`aom inspect --changes` full-parses the target session, derives changed-task records via `extract_changes`, and can render a module-level before/after diff with `--diff`; `--warnings` likewise extracts warnings with optional host/play/task filters and JSON output. [`src/ansible_aom/inspect/cli.py:55-126`](../../../../ansible-aom/src/ansible_aom/inspect/cli.py#L55-L126), [`src/ansible_aom/inspect/cli.py:243-287`](../../../../ansible-aom/src/ansible_aom/inspect/cli.py#L243-L287), [`src/ansible_aom/inspect/formatters.py:156-241`](../../../../ansible-aom/src/ansible_aom/inspect/formatters.py#L156-L241) The changelog confirms these additions and their output intent. [`CHANGELOG.md:12-16`](../../../../ansible-aom/CHANGELOG.md#L12-L16)

One documentation discrepancy matters: `SPECIFICATION.md` still advertises legacy `inspect list`, explicit session arguments, `inspect diff <id1> <id2>`, and export, while the actual inspect CLI says those legacy subcommands were removed and only parses `prune` as a subcommand. Trust the code: AOM presently has change-detail diff, not a current cross-session diff CLI. [`SPECIFICATION.md:287-303`](../../../../ansible-aom/SPECIFICATION.md#L287-L303), [`src/ansible_aom/inspect/cli.py:1-17`](../../../../ansible-aom/src/ansible_aom/inspect/cli.py#L1-L17), [`src/ansible_aom/inspect/cli.py:294-344`](../../../../ansible-aom/src/ansible_aom/inspect/cli.py#L294-L344)

The known operational pain is also clear in source: one large event could previously spend 50–500 ms in synchronous `write`, freezing the live tree, leading to the async bounded/drop-on-overflow design. Its concurrent-inspect test intentionally creates a 1,000-event/s writer/reader race and asserts snapshots never treat truncated lines as events. This is a good live-tail stress test, but it also confirms AOM accepts recording loss under pressure. [`src/ansible_aom/session/store.py:139-145`](../../../../ansible-aom/src/ansible_aom/session/store.py#L139-L145), [`tests/integration/test_concurrent_inspect.py:9-21`](../../../../ansible-aom/tests/integration/test_concurrent_inspect.py#L9-L21), [`tests/integration/test_concurrent_inspect.py:367-373`](../../../../ansible-aom/tests/integration/test_concurrent_inspect.py#L367-L373)

## 3. Comparison and storage recommendation

### Current triplum facts

Triplum already has a single SQLite metrics store opened in autocommit mode with WAL and foreign keys. It stores run identity/config/status, per-question outputs and retrieved chunk IDs, timed/priced stage events, price snapshots, and artifacts; run lookup only reuses `status = 'ok'` records. [`python/triplum/bench/runstore.py:16-72`](../../python/triplum/bench/runstore.py#L16-L72), [`python/triplum/bench/runstore.py:117-160`](../../python/triplum/bench/runstore.py#L117-L160)

The runner creates a `running` record and snapshots prices before pipeline work. It writes reader/judge stage records and then adds a question row after that question’s work; in `finally`, it closes the graph store and updates final run status/counters. Consequently, a process crash can leave already-autocommitted event/question rows and a `running` run, but today there is no resume lookup for that run because `find_run` selects only `ok`. [`python/triplum/bench/runner.py:64-113`](../../python/triplum/bench/runner.py#L64-L113), [`python/triplum/bench/runner.py:134-188`](../../python/triplum/bench/runner.py#L134-L188), [`python/triplum/bench/runstore.py:121-127`](../../python/triplum/bench/runstore.py#L121-L127)

Its call cache is intentionally minimal: canonical JSON is SHA-256 keyed, one payload file lives under `<root>/<first-two-hex>/<key>`, and `put` writes a unique temporary file then atomically replaces the final path. It has no metadata, listing, eviction, index, fsync, or pruning API. [`python/triplum/cache.py:1-5`](../../python/triplum/cache.py#L1-L5), [`python/triplum/cache.py:17-56`](../../python/triplum/cache.py#L17-L56) The public contract already promises content-addressed full-effective-request caching, per-machine scope, exact config display/re-run, price snapshots, and one event row per call/stage. [`docs/benchmarking.md:29-67`](../benchmarking.md#L29-L67)

### Recommendation: keep SQLite only

For the stated workload (20–1,000 questions × 2–5 calls, tens of runs, and a finished-question durability requirement), **keep SQLite as the only primary store**. It is already the authoritative source for precisely the fields benchmark inspection/diffing needs and avoids duplicating every result in both a JSONL log and a derived index. The important missing piece is resume semantics, not an event-format replacement: add a query for a matching `running` identity, reuse its run ID, and skip `question_id`s already present in `run_questions`. The existing primary key gives the necessary idempotence boundary. [`python/triplum/bench/runstore.py:27-33`](../../python/triplum/bench/runstore.py#L27-L33), [`python/triplum/bench/runstore.py:121-152`](../../python/triplum/bench/runstore.py#L121-L152)

I do **not** recommend JSONL primary + SQLite derived: it imports AOM’s extra index lifecycle and, if copied literally, its loss-on-overflow trade-off; neither fits “should not lose finished questions.” I also do **not** recommend a broad JSONL export now: it adds a second format without enabling resume or the proposed tools. A narrow future `bench export --jsonl` is reasonable only if portable audit interchange becomes an actual requirement; that would be an export, not a writer.

## 5. Decisions we recommend and open questions

### Decisions we recommend

1. Keep `runs.db` SQLite-only as the run-store source of truth; do not adopt AOM’s JSONL-primary plus derived-index architecture for the current benchmark workload. The existing schema, WAL setup, and per-question primary key align more directly with resumable benchmark work. [`python/triplum/bench/runstore.py:16-72`](../../python/triplum/bench/runstore.py#L16-L72), [`python/triplum/bench/runstore.py:27-33`](../../python/triplum/bench/runstore.py#L27-L33)
2. Implement explicit `--resume` by identity, completing missing question IDs in the same run. Do not copy AOM’s drop-on-overflow writer behaviour because it conflicts with retaining completed questions. ### Open questions

1. Should `--resume` be default for a matching `running` identity, or opt-in until users are accustomed to reusing partial results? The current contract only reuses `ok` runs and `--force` always creates a new run. [`python/triplum/bench/runstore.py:121-145`](../../python/triplum/bench/runstore.py#L121-L145), [`docs/benchmarking.md:44-55`](../benchmarking.md#L44-L55)
2. What is the completion boundary for a question with a judge: reader result, judge result, and `run_questions` row are currently written as separate autocommit operations. Resume needs one stated policy for a crash between them, ideally one transactional “question complete” unit. [`python/triplum/bench/runner.py:138-177`](../../python/triplum/bench/runner.py#L138-L177), [`python/triplum/bench/runstore.py:221-243`](../../python/triplum/bench/runstore.py#L221-L243)
3. How long must passage drill-down remain reproducible? Current records retain IDs and a store artifact path/checksum, not passage text; the answer determines whether artifact pinning is sufficient or a per-run snapshot is warranted. [`python/triplum/bench/runstore.py:27-55`](../../python/triplum/bench/runstore.py#L27-L55), [`python/triplum/bench/runner.py:158-178`](../../python/triplum/bench/runner.py#L158-L178)
4. Are raw model prompts/responses permitted in any human-facing inspection artifact? AOM’s redaction experience shows that once verbose payloads are persisted, redaction must be designed before the writer, not bolted onto display. [`src/ansible_aom/core/redaction.py:1-27`](../../../../ansible-aom/src/ansible_aom/core/redaction.py#L1-L27), [`ARCHITECTURE.md:300-304`](../../../../ansible-aom/ARCHITECTURE.md#L300-L304)
5. Is cache management actually needed at expected local-cache sizes? There is no current triplum cache metadata or retention contract, while its benchmark contract describes it only as a per-machine optimization. [`python/triplum/cache.py:33-56`](../../python/triplum/cache.py#L33-L56), [`docs/benchmarking.md:29-42`](../benchmarking.md#L29-L42)
