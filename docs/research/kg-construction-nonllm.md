# Non-LLM knowledge-graph construction baselines

Snapshot 2026-09-17. A Codex (GPT-6-astra) research pass with web access and no repository
access, kept verbatim below its own title apart from this header. It answers what a fully local,
non-LLM extraction stack can look like in September 2026 so that LLM extraction (sub-project 2b)
has a cheap, deterministic comparator. Its recommendation, spaCy plus explicit dependency rules
and conservative string resolution first, with GLiNER/GLiREL as a separate accuracy experiment,
is what the [previous foundation](../notes/previous-foundation.md) adopted; the companion dependency
resolutions it produced are not kept. Evidence labels (V, P, E, U) are the pass's own.

---

Research date: **17 September 2026**. Scope: English Wikipedia, news and scientific text; local inference on Apple Silicon; Python 3.12/3.13. No private repositories were accessed and no subagents were used.

**Recommendation:** establish spaCy plus dependency rules and conservative string resolution as the primary baseline. Add GLiNER–GLiREL as a separate accuracy experiment. Neither the available measurements nor the package metadata establish that a neural NER–relation–coreference pipeline achieves 20 chunks/second on an unspecified laptop.

## Evidence and measurement conventions

**V** means checked against an official page, public source file, package registry or model card during this research. **P** means a published measurement, verified in its source today; it is not a new measurement. **E** means an engineering estimate or extrapolation. **U** means unverified or not reported. No recommendation relies on an unlabelled number recalled from memory.

Package versions below are the latest PyPI versions observed today unless identified as a proposed pin or source revision. Release dates and Python requirements were obtained from the project's PyPI JSON endpoint, whose pattern is `https://pypi.org/pypi/<package>/json`; the collected responses are in `pypi-evidence.json` (not kept). Repository activity is recorded in `repo-metadata.json` (not kept). A recent push is evidence of activity, not proof of support or maintenance quality. An old release alone does not prove abandonment.

Python status: **W** = relevant wheel/classifier verified; **M** = metadata permits the interpreter, dependency/runtime support untested; **X** = published constraints or historical dependency pins conflict; **J** = Python client can call a separate JVM process. Unless stated otherwise, M applies to both 3.12 and 3.13. A pure-Python wheel does not establish that its native dependencies install.

For planning, a **chunk means 200 words**, processed in batches after model loading. Twenty such chunks/second requires 4,000 words/second. Most papers measure sentences, documents, tokens or GPU batches instead. All size estimates use decimal MB/GB and distinguish model downloads from installed environments. No extraction models were run for this report.

The spaCy metadata numbers describe the released pipelines' evaluation, not a fresh CoNLL03 leaderboard. GLiNER's zero-shot card evaluation is also not comparable to supervised, dataset-specific SpanMarker scores. Repeating “GLiNER beats conventional NER” without fixing labels, training regime and evaluation protocol would be misleading.

Use **`en_core_web_sm`** initially: dependency OpenIE already needs its parser, and this avoids a second encoder. Keep noun-phrase arguments as spans even when NER does not label them. Scientific entities such as methods, tasks and materials are often common nouns; a PERSON/ORG/GPE extractor is not an adequate scientific span detector. Add a separate GLiNER run with the target dataset's type vocabulary, or train a domain span model, rather than silently treating general-purpose NER labels as scientific coverage.

The historical spaCy-lg rate extrapolates to **50 chunks/s E** at 200 words, versus **3.4 E** for trf, **4.4 E** for Stanza's cited pipeline and **1.6 E** for Flair's. These conversions illustrate the scale of the throughput constraint; different hardware, component selections and sentence lengths prevent treating them as laptop predictions. Benchmark `nlp.pipe` with the actual length distribution and include tokenization.

The main choice is between **open predicates** and **schema classification**. `founded`, `was founded by` and `established` require an explicit normalisation policy before comparison with `P112`. GLiREL lets the experiment supply the relation vocabulary; REBEL has a learned vocabulary and generates strings. Neither guarantees a valid PID without an adapter. ReLiK's linking configuration is a different task from its NYT relation model.

For a minimal baseline, implement a small set of dependency patterns directly. Textacy is a useful reference, but adds dependencies without supplying a comprehensive OpenIE system. Cover active/passive transitive clauses, copulas, appositions and carefully bounded coordination. Preserve negation, modal auxiliaries and attribution. Dropping “not” or converting “may cause” into “causes” creates false facts, even when the triple is syntactically well formed.

REBEL is worth retaining as a historical comparison, but BART-large is small only relative to contemporary generative LLMs. Autoregressive decoding costs, generated rather than grounded spans, and noncommercial weights make it a weaker default for this brief. `spacy-llm` is excluded throughout.

Start with corpus-scoped exact aliases, type constraints and a small labelled set of ambiguous pairs. Add RapidFuzz only within compatible candidate blocks. “Washington” and “Washington University” illustrate why high lexical similarity is insufficient; “IBM” and “International Business Machines” illustrate why low similarity is insufficient. Embedding similarity has the same fundamental limitation: related entities are often close without being identical.

Separate mention clustering, external linking and predicate canonicalisation in evaluation. CESI and later work explicitly model OpenIE noun/relation phrases; record-linkage systems assume useful structured attributes. A 2024 research survey discusses multi-view/context approaches and the limitations of sparse open-KG structure. These are research alternatives when simple resolution measurably fails, not prerequisites for the baseline. [Open-KB canonicalisation survey](https://ceur-ws.org/Vol-3747/text2kg_paper5.pdf)

External linking should be optional in the first baseline. A corpus-local canonical ID is sufficient for comparing graph construction and retrieval if all systems use the same evaluator alignment. Introducing a full Wikipedia index changes memory, candidate coverage and entity priors simultaneously. If external IDs are required, first build a restricted alias/title index for entities represented in the evaluation corpus, explicitly reporting that closed-world candidate advantage.

Do not force NIL mentions into Wikidata. Scientific concepts and novel entities need local IDs. Likewise, Wikipedia page titles, page IDs and Wikidata QIDs are distinct identifiers: use a versioned mapping, not string substitution. Report linking accuracy separately from mention detection and relation classification. The ReFinED document rate and ReLiK GPU timings cannot be converted into end-to-end chunk throughput without document lengths and configuration.

## 6. Temporal expressions

| Tool | Version / licence | Install / maintenance | CPU path and limitations | Source |
|---|---|---|---|---|
| SUTime | CoreNLP **4.5.10**, GPL-3.0 | Java; Stanza client usable on 3.12/13 | Rule-based TIMEX3 extraction and normalisation; document date anchors relative expressions; throughput U | [SUTime](https://stanfordnlp.github.io/CoreNLP/sutime.html) |
| HeidelTime | **2.2.1** documented release; GPL-3.0 | Java/UIMA or standalone; current release cadence U | Domain-aware rules, TIMEX3; news/narrative/scientific distinctions; throughput U | [Official project](https://github.com/HeidelTime/heideltime) |
| `dateparser` | **1.4.3**, BSD-3-Clause | W classifier; Sep 2026 | Normalises candidate text; date searching explicitly documented as limited. Fix language and relative base | [Docs](https://dateparser.readthedocs.io/en/latest/), [package](https://pypi.org/project/dateparser/) |
| spaCy DATE/TIME + dateparser | Above versions; MIT + BSD | Recommended native Python route | NER proposes spans; normalisation does not determine which fact the time qualifies | [spaCy labels](https://spacy.io/models/en), [dateparser settings](https://dateparser.readthedocs.io/en/latest/settings.html) |
| `timexy` | **0.1.3**, MIT | Last PyPI release Mar 2022; 3.12/13 U | spaCy component for English/German/French; TIMEX3/timestamp output; throughput U | [Repo](https://github.com/paulrinckens/timexy), [package](https://pypi.org/project/timexy/) |

Practical route: collect DATE/TIME spans plus explicit year/range patterns; parse with `languages=['en']`, a fixed document-relative base and a declared date-order policy; retain original text and precision. Interpret a year as a year interval, not an invented day. Recognise “from 2010 to 2012”, “since 2010”, “until 2012” with explicit rules, retaining open ends and endpoint ambiguity. Attach candidates to the predicate using dependency/clause scope, not merely sentence co-occurrence.

Temporal mention normalisation is **not fact-validity inference**. “In 2020 Alice said Bob joined in 2018” contains an assertion time and an event time. “Alice was born in 1980” supplies a birth-date literal; it does not make the birth relation valid only during 1980. Keep candidates and attachment rationale in extractor evidence; populate `valid_from/valid_to` only when the relation's temporal semantics justify it. Unresolved relative dates remain unresolved if the document date is absent.

Adopt an explicit interval convention, for example half-open boundaries, but do not silently turn an uncertain endpoint into certainty. Persist granularity and the reference date alongside support metadata. For reproducibility, never let dateparser use today's clock implicitly: rerunning a historical chunk next month must not change its facts.

“Atomic” is an annotation decision, not a guaranteed property of clause splitting. Split coordinated predicates only when argument sharing is syntactically justified. Preserve attribution (“the report claims”), negation, conditions and relative-clause attachment. Do not promote a conditional consequent into an asserted fact. The inexpensive baseline should return structured clause spans and qualifiers rather than generate rewritten sentences; this keeps its evidence auditable and avoids a new text-alignment problem.

DisSim/Graphene are appropriate historical comparison systems when reproducing that literature. They are poor mandatory dependencies for a modern Python-only sandbox. If decomposition improves relation recall, evaluate whether the extra triples remain entailed, rather than rewarding triple count alone.

The model IDs, revisions and file sizes were read from the official [GLiNER](https://huggingface.co/gliner-community/gliner_small-v2.5/tree/f227d3cd637bd4e6757ae143935316d062393341), [GLiREL](https://huggingface.co/jackboyla/glirel-large-v0/tree/40a523e12a8432d6da364cf2a195a28755ff04d3) and [F-Coref](https://huggingface.co/biu-nlp/f-coref/tree/e91dfff12879495d882ba9460d0c5d5dd44ade59) inventories. Package pins are proposals, not claims of a jointly supported upstream distribution. GLiNER 0.2.29 permits Transformers >=4.51.3 and <5.17; the older pin isolates this experiment from Transformers 5 changes. fastcoref's current source requires Transformers >=5.9 and is a different experiment.

“Deterministic” means fixed models, rules, thresholds, ordering and environment. spaCy's parser/NER are neural; this stack is not rule-only. Use CPU inference without stochastic decoding; do not promise bit-identical floating-point results across different dependency versions or hardware. For the small stack, GLiREL token indices are inclusive whereas spaCy spans use an exclusive end; validate the adapter before scoring. [GLiREL input convention](https://github.com/jackboyla/GLiREL)

If a historical REBEL run is wanted, replace GLiREL with `Babelscape/rebel-large` revision `44eb6cb4585df284ce6c4d6a7013f83fe473c052`, using the same Transformers/PyTorch pins. Its weights are 1.625 GB and NC-SA-4.0. Use greedy decoding (`do_sample=False`, one beam) as a declared speed baseline; a beam-search result is a separate configuration. Ground generated entity strings back to the chunk; unmatched or ambiguous spans must not become fabricated mentions.

For the canonical tables, create a mention for every grounded argument; apply resolution to obtain `canonical_id`; emit an entity object or typed literal, never both. Deduplicate fact identity separately from support: two extractors agreeing on a triple should add support rows, not erase the source-specific outputs needed for comparison. Preserve extractor version, model revision, original spans and raw scores. Rule confidence should be a declared heuristic or null, not disguised as a calibrated probability.

Run an evaluation ladder: spans → relations with gold spans → end-to-end triples → canonicalisation → retrieval. Freeze chunking, corpus splits, relation mappings and thresholds before the test split. Report micro precision/recall/F1, missing-support rate, literal accuracy and throughput with word/token length distributions. Include a small manual audit of unmatched predictions because incompletely annotated corpora penalise valid extractions too. Keep gold entity resolution as an oracle ablation, not hidden preprocessing.

For performance, measure cold download/load time separately from steady state; record chip, RAM, macOS, thread count, batch size, precision and model revision. Warm up, then process at least 1,000 representative chunks with every enabled stage. Report median and tail latency, chunks/s, words/s and peak resident memory. A high NER-only rate cannot certify the full pipeline, particularly with document coreference or many GLiREL entity pairs.

### Verification limits and install artifacts

The report's companion `*.in` files specify the proposed stacks; `deterministic-py312.txt`, `deterministic-py313.txt` and corresponding small-model resolution files, when present, record dependency solutions. Resolution is **not installation, import testing, inference testing or a benchmark**. No model performance or total installed size was measured locally. Unknown licence grants, missing CPU results and legacy framework compatibility are deliberately labelled rather than filled from memory.

The strongest remaining uncertainties are GLiREL's conflicting licence declarations, actual small-stack runtime compatibility, throughput on the user's chip and chunk distribution, scientific-domain span recall, and linking-index resident memory. None prevents the deterministic baseline from being the first implementation; each should be isolated in the later model comparison rather than buried in its setup.
